== Blocking fact: no `chora-registry` entry exists for vocarium

Re-verified against the public registry at the pinned seed commit
`235e877e86858c79941614f7fc6f0c6ecf60846db7519` (clone clean at that pin):
a case-insensitive search for `vocat|ocari` matches only the word
"behaviour" in `.github/CODE_OF_CONDUCT.md`. There is no vocarium `(repo …)`
entry, no minted repository UUID, and no clade placement.

Consequences, all visible in the tree today:

* `vocarium_chora.deed` carries
  `:repo-uuid #u8"chora-registry:github.com/hyperpolymath/vocarium"` — a
  deterministic *profile-C name*, not a `#uuid` mint. The file header says
  so, and `DEED-MIGRATION.adoc` repeats it.
* The four descriptiles carry
  `:of-chora #u8"chora-registry:github.com/hyperpolymath/vocarium"` under
  the same profile-C convention.
* `vocarium_chora.deed` proposes `(clade :primary db …)` with an explicit
  rationale ("Pending confirmation by chora-registry; the old rm/gv
  placement described the template, not this repo."). It is a proposal;
  the registry and the owner decide. The old `rm`/`gv` clade described the
  `rsr-template-repo` the repo was instantiated from.
* `0-AI-MANIFEST.deed` and the descriptiles are read by `validate-deed.sh`
  today, but nothing in the estate treats them as authoritative until the
  registry confirms identity and placement.
* The merge is not registered work under the registry's rules: placement,
  minting and affirmation are the registry's to decide, and an entry, once
  made, is never removed (registry policy, ADR 0008).

== The registration bundle (ready to file in `hyperpolymath/chora-registry`)

*Draft — not filed from this branch.* Filing is a change to a different
repository and is the owner's (or the registry owner's) act. ADR 0008 lets a
registration be merged by the owner; `sync/uuid-v8.sh` is the registry's
mint tooling. Do not compute-and-commit an id into vocarium.

[source]
----
(repo :name "vocarium" :owner "hyperpolymath"
      :uuid #uuid"<minted by chora-registry tooling at the birth path —
                  never copied or guessed>"
      :minted-in chora-registry
      :description "A structured store of vokeable particulars, transformations, grades, warrants and verdicts."
      (lineage :type standalone :instantiated-from "rsr-template-repo")
      (placement :scheme clade-12 :category db :primary #t))
----

Notes for the filer:

* The description above is lifted verbatim from
  `vocarium_chora.deed` (`(purpose :text …)`) — owner edits welcome before
  filing.
* The proposed `category db` comes from the same deed's clade rationale, not
  from this document. Categories in the seed used as reference points
  (facts, not recommendations): `haec` holds `fv` primary (rank 1 for `nl`),
  and `trope-checker` / `trope-particularity-workbench` hold `rm` primary.
  The owner decides vocarium's category at filing time; `db` is the only
  value consistent with the deed as merged.
* Birth path for the profile-C computation: `github.com/hyperpolymath/vocarium`.
* `:beholding-chora` for the estate chora, as read from the registry seed at
  the pinned revision: `#uuid"0889b37b-defb-831f-973c-e119500db00e"`.
* If ADR-008 profile C were applied today with the `chora-registry` domain,
  `SHA-256("chora-registry:github.com/hyperpolymath/vocarium")`, truncated to
  16 bytes with the version-8 nibble and RFC 9562 variant, yields
  `31c90719-e7d5-8162-8356-558d6ab6e9fd`. With the legacy `gv-clade-index`
  domain (pre-V9 ids), the same computation yields
  `9029d13d-f348-8c6e-8e4b-f06d6ef5d5ef`. *Neither is an id of record.*
  Which domain applies is the registry's call (V9 2026-11 vs this
  repository's 2026-06-26 birth per `CLAUDE.md`) — the owner rules at
  filing; the registry mints; vocarium is then re-pointed.
* Lineage is `standalone`, instantiated from `rsr-template-repo` — that is
  what the deed states; the registry may classify it differently.
